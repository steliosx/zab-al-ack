A review that only changed the prose

2026-09-13 · candidate 0.1.0a16

The independent review of a15 rebuilt the wheel to the same bytes, reran every offline suite to the same numbers, and found no defect in the code. What it did find was five claims in our own release notes that were not quite true. That is a useful kind of review, and it is worth writing down what it caught.

“Shipped in every handoff since a7”

We said the owner-only evidence file had gone out in every handoff since a7. It hadn’t. Reading the stored mode out of each delivered archive gives a3/a4/a5/a8 0644, a9 0644, a10 0600, a11 0644, a12 0600, a13 0600, a14 0644, a15 0644.

The writer really was wrong the whole time — a fresh a14 run still produced 0600 — but whether a reader ever saw it depended on who assembled the packet. Ours copies source files with their modes intact, so it published whatever the writer left. The other producer’s normalised everything to 0644 and hid the problem. The distinction matters: one sentence was about the code, the other about the delivery, and we had run them together.

“Both required by the audit”

We described the two per-profile mutation records as required by the export audit. Delete both from a copy of the tree and the audit reports nothing. They are validated when present and optional when absent. The rule is fine; our description of it was wrong.

Whose run is it

We wrote that a15’s service runs “describe a14’s behaviour too”, because a14 changed no service-path file. Unchanged code is grounds for an inference. It does not turn a NOT_RUN record into an execution, and a release note is exactly the wrong place to blur that.

Two files we said weren’t there

a15’s review table claimed no owner-only record remained in the handoff. Two do, both retained from the a7 packet exactly as received, and they are the only two of that directory’s twenty-one records below 0644 — the defect drawn in outline. One of them is a NOT_RUN real-Zabbix record, which quietly disposes of another a15 claim: we said that instance stayed invisible because no candidate could run the suite, when in fact the NOT_RUN branch uses the same writer and the mode had been sitting in a shipped artifact since a7. Nothing had looked at exported modes as a class until we added the rule that found it.

The machine-readable check had it right all along; only the prose was wrong. That is its own small lesson about which artifact to trust.

What a16 adds

The review’s ten writer regressions, kept as they were meant: both public writers and both private ones, under a permissive and a restrictive umask, including replacement of an existing 0600 file. They discriminate — against an unmodified a14 checkout the four public cases fail on the mode itself and the other six fail because a14’s writers took no mode argument at all. All ten pass here. The changelog’s old “Still owner-only” headings are now “Still pending”, so the phrase cannot be read as a file mode. And the release verifier is no longer advertised as stdlib-only, because it reaches PyYAML through the guidance validator.

No runtime change, no SQL change, no new migration. Still open, unchanged: the webhook transport limitation A2, the Docker Compose forms, hosted CI, signed attestation, and the eight deployment gates.

Zab-al-ack is independent of Alerta and Zabbix. Public package and repository ownership are still being prepared. The website is informational and does not connect to monitoring systems.
