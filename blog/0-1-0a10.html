The renamed code meets real services

2026-09-12 · candidate 0.1.0a10

a9 renamed everything and said so plainly: the native database phases, the real Zabbix contract and the deployment lab had not run on the new namespace. a10 runs them. Nothing broke.

What ran

Forty-one native cases on a source-built PostgreSQL 18.3 with PgBouncer 1.24.1, in five fresh clusters — including the new guard that refuses a database still holding an ackline schema. Five real Zabbix 7.0.10 cases through the execution-owned recorder, with [zabalack] comments read back from the disposable instance. The deployment lab’s four cases and all thirteen observations, from the installed wheel, not an editable checkout.

Why the wheel matters

The independent a8 review made a fair point: a service run from an editable source install proves the source, not the package, and a bootstrap that lives outside the repository cannot be repeated. So a10 ships the two runners it used. tools/native_local.py imports the Compose runner’s phase table and reproduces its environment on locally installed services. tools/run_deployment_e2e_local.py executes the unmodified lab against operator-provided services and refuses a runner environment that imports the checkout or an editable install; it compares the installed bytes with the wheel and records the wheel’s hash.

What it does not claim

These are local processes, labelled as such in every record. The Docker Compose forms, hosted CI, signed attestation and the eight deployment gates are still open. A2 — the webhook transport that does not verify TLS peers — is unchanged and still blocks deployment.

The a9 packet itself checked out: checksums, bundle, byte-identical rebuilds, and the same 796 reference passes. The mechanically renamed a8 tree differs from a9 only where a9 said it would.

Read the evidence notes or docs/local-services.md in the source handoff for the operator inputs.
