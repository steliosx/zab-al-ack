Testing the integration against Zabbix 7.0.30

2026-09-12 · independent review of 0.1.0a12

An integration earns confidence at the boundaries between its systems. We built Zabbix 7.0.30 from its official source and put the a12 candidate through a disposable lab, alongside the original 7.0.10 reference. The review found a permission-fixture defect that a successful acknowledgement alone had not exposed.

A recent LTS, in a real service lab

Zabbix 7.0.30 is the recent 7.0 LTS patch used in this review. A full Ubuntu virtual machine lets PostgreSQL use ordinary unprivileged operating-system users and real SQL logins. PostgreSQL 18.3, PgBouncer 1.24.1 and both Zabbix servers were built from source; the guest network was restricted and the test services listened on loopback.

The corrected reference suite records 818 passed, 22 skipped and no failures. The native run adds 42 passed across database, delivery-failure, worker, Alerta and functional batch phases. These layers are reported separately; emulated timing does not establish production capacity.

Both Zabbix versions passed all five contract cases and all ten supplemental API cases, with no skips or failures. The installed-wheel 7.0.10 pipeline also passed all four tests and 13 observations, with successful cleanup. These records identify the final corrected harness; earlier attempts are retained separately.

Ask what the token can actually do

The old lab provisioner set the default action permission to disabled. Zabbix nevertheless preserved enabled values for individual rules that the request omitted. A real negative test showed that its synthetic worker could suppress a problem. An inspection of both upstream versions explained why.

The corrected helper now lists every inspected action and UI rule explicitly, then reads the effective role back before creating a user or token. Missing, duplicate, unexpected or broader permissions stop provisioning. Eight new regressions check this guard, and the mock now models Zabbix’s omitted-rule behavior. The plugin’s runtime and SQL remain unchanged.

There is a second boundary to understand: Zabbix shares one role capability between acknowledging and unacknowledging. Zab-al-ack’s client permits only acknowledgement actions 2 and 6, but the upstream token’s authority is broader. Keep token protection and effective-role checks in your deployment plan.

Keep the failed attempts

The first supplemental run had five failures. Three concerned the intended role-denial boundary; two came from our new tests assuming string result IDs where Zabbix returned integers. The existing client already handles both forms. The review packet keeps that failed run and the regression that fails on unmodified a12, alongside the corrected results. It does not count retries as extra acceptance coverage.

The review also added a staged-import regression so the new role helper travels with the Docker build context. A cold setup request took 13 seconds under CPU emulation; only the isolated provisioning client’s bound increased to 30 seconds. Production delivery deadlines and test assertions remain unchanged, and the final run records identify this revised harness.

A view of the original lab

A later pipeline attempt passed 12 of its 13 observations but failed its immediate projection sample after ledger completion. The retained database eventually showed the correct projection; the exact field that failed at the earlier sample was not recorded. A read before the separate projection commit is the inferred cause. The lab now waits within a fixed bound for the original complete event, status and history checks. A regression rejects incomplete or mismatched states. This changes the observer, not the worker or SQL, and the failed attempt remains in the review packet.

What remains open

The webhook’s TLS and redirect limitation, recorded as amendment A2, remains unresolved. The current artifact does not enable the peer and hostname verification options inspected in 7.0.30, and redirects are followed. Successful loopback delivery does not authenticate a production ingestion path. The separate worker HTTP client verifies TLS and refuses redirects.

Production gates G1–G8, deployed permissions, update-operation inventory, HA and fleet capacity still require your environment’s evidence. Docker Compose execution, hosted workflows, signed attestation and external security review are also separate work. The website stays informational, with no monitoring connections or credential forms.

Start with the test evidence and commands, the transport limitation and the illustrated workflow.
