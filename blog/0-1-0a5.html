Binding test evidence to the code it ran

2026-09-10 · candidate 0.1.0a5

Ackline release history. The project is now Zab-al-ack; this post retains the names and results recorded for this candidate.

Two reviews in a row asked the same question: how do you know a passing report belongs to this tree? Until a5 the answer was "because we say so". Run records now carry two digests, one over the implementation and one over the tests, runners and labs, computed before the run starts. The acceptance mapper, export audit and build compare those digests with the current tree. This catches stale or mismatched results; an unsigned hash does not prove who ran a test or that its report is truthful.

We demonstrated it the boring way: edit one test file, and mapping, audit and build all refuse until the runs are repeated. That is the point. It cost us an extra native run when we later fixed a flake, and it should.

The a4 review's two tooling findings are adopted unchanged: the lab fixtures validate the exact loopback URL before touching a network or a token, and the acceptance validator rejects contradictory service evidence. The negative-visibility case now proves the outside event exists, through a separate read-only witness token, before requiring the restricted token to see nothing.

The flake, for the record: three consecutive updates with identical marker text within one PGlite millisecond, which the capture trigger correctly ignores. The test was wrong, not the trigger.

Details for this candidate are in the cumulative changelog and the release amendments shipped with the source. Nothing on this page is a production or publication claim.
