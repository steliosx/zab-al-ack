What a review is for

2026-09-12 · candidate 0.1.0a13

An independent reviewer built Zabbix 7.0.30 from source, put a12 through a disposable virtual machine, and found something our own green test run had been quietly hiding for six candidates: the lab role we described as “only acknowledge and comment” could suppress problems.

Why a passing test can be wrong

The lab created its restricted role with actions.default_access: 0 and a list of two actions. That reads like default-deny. It is not. On Zabbix 7.0 the rule compiler keeps the previous, enabled value for any individual rule the request omits, so every other action stayed on. The two denials the old lab did observe — close and severity — came back with “No permissions to referred object”, which is the host-rights boundary. The role was never doing the work we credited it with.

We did not take that on trust. Before adopting anything we recreated the original role on our own 7.0.10 server: the read-back showed all eleven actions enabled and a real suppression request was accepted. With the corrected, fully enumerated rules the same three requests came back as “no permissions to suppress problems”, “…to close problems”, “…to change problem severity” — the denial we had been claiming all along.

One boundary the review also names

Zabbix maps acknowledging and unacknowledging to a single role capability. We confirmed it: a token whose role enables acknowledge_problems accepted action 16. Zab-al-ack’s client only ever sends actions 2 and 6, so the integration does not unacknowledge — but the token itself could. That belongs in your token-protection plan, not in a footnote.

What a13 adds

The review corrected the deployment lab’s provisioner, which now enumerates every inspected action and UI rule and verifies the effective role through role.get before any user or token exists. a13 takes that unchanged, with its ten regressions, and extends it to the place the review did not reach: the fixture an operator provisions by hand for the real-Zabbix suite. Ours turned out to carry script execution, API-token management and more, contained in practice only by the API method allowlist. The instructions now require enumeration and read-back, and the suite proves the boundary on the live server by demanding the specific suppression denial — a host-rights rejection is explicitly not accepted as evidence.

Everything else was re-run here: 820 reference tests, 42 native PostgreSQL and PgBouncer cases, six real Zabbix 7.0.10 contract cases and the installed-wheel pipeline’s four tests with thirteen observations. The runtime code and SQL did not change.

What it still is not

A passing disposable fixture does not close G5: your deployment still needs an effective-role read-back and positive and negative permission tests on the approved account. A2 — the reference webhook does not verify TLS peers and follows redirects — is unresolved. The Docker Compose forms, hosted CI, signed attestation and the eight gates remain open.

Read the review itself, or the amendment A4 write-up in the source handoff.

Zab-al-ack is independent of Alerta and Zabbix. Public package and repository ownership are still being prepared. The website is informational and does not connect to monitoring systems.
