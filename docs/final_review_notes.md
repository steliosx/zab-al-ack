# Final-review interpretations applied to preserved revision 1.2

The public site-neutral design is in `DESIGN.md`. These four interpretations are authoritative release-one clarifications, not a new architecture.

1. In the first underlying-privileges paragraph of baseline §8, read the sentence without the obsolete phrase **“or source-identity columns.”** The later boundary table and T38 govern. Source identity lives in JSONB `attributes`; `UPDATE(attributes)` is a column permission and cannot constrain individual JSON keys. The trusted function owner can change arbitrary keys in that column. The projection implementation's approved-key merge and tests protect its callable interface; the worker has no direct table modification grant. Separately protected `status`, `severity`, `history`, and `customer` columns remain outside the owner's update grant.
2. A marker-dependent trigger does not run for an acknowledgement with no marker. While plugin bypass is active, evidence is the plugin projection, committed history and operator change audit. A **marked** candidate reaching an enabled trigger while the database capture-disable flag is active can produce a bypass diagnostic. A physically disabled trigger produces no diagnostic. Staged projection attributes alone never prove an acknowledgement was saved.
3. Flag bypass depends on its configuration/function/diagnostic path working. If that path is itself broken, separately authorised physical trigger disable is break-glass fallback. The worker and probe cannot set bypass, attach/replace a trigger, or enable/disable it. A `TRIGGER` grant can permit installation but does not grant the table ownership required for `ALTER TABLE ... DISABLE TRIGGER`.
4. §12's data-classification table has no row for the Alerta attribute layer. Read the classification for that layer from `security_and_data.md` ("Alerta projection"), and read it as a constraint on **readers**, not merely on export tooling. A reserved `zabbix_ack_sync*` name marks a key as owned by this integration; it does not classify the key's contents as suitable for anyone who can read the alert. Reserved attributes may legitimately carry restricted staging data during capture — §5.2's intent payload is exactly that, and §5.1 already records that such attributes are persisted before the acknowledgement history write — but restricted staging data must never be reader-visible at any point in its life. That includes before capture, while capture is pending, and where capture never occurs at all, and it covers every reader-facing surface, not only response bodies: an authenticated search predicate that can test the value discloses it as surely as returning it. Amendment A5 records the reference-source behaviour that makes this reachable, the affected paths and the two-stage correction. The frozen §12 text is unchanged; this interpretation supplies the missing row rather than editing the baseline.

See `rollback.md` for the ordered operational procedure and `acceptance_matrix.csv` for T38/T39 evidence status, and `SPEC_AMENDMENTS.md` A5 with T40/T41 for the attribute-layer confidentiality status. These interpretations do not close G1–G8.
