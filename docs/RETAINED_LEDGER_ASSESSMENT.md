# Retained-ledger assessment plan

This assessment supplements the frozen `0.1.0a16` ARM64 candidate at PR #24
`7ae972e8488ab9602c60a4895a98e1204d534207`. It does not establish production
capacity or approve a retention policy. Measurements and their actual dataset
are recorded separately from this plan; unavailable dimensions remain unmeasured.

## Completed bounded measurement

The [native batch run](ARM64_BATCH_QUALIFICATION.md) retained 500 captures,
actions, effects, outbox rows, outcomes and alert generations, plus 250 write
attempts. Captures span 00:48:06.483342–00:49:12.291654 UTC on 18 September 2026.
All actions were terminal `ok`; there was one customer/instance/cohort, no old
backlog and no retention deletion or artificial aging. Total Zabalack table,
index and associated storage reported by `pg_total_relation_size` was 3,457,024
bytes. Counts and live/dead estimates were retained, including 148 estimated
dead action tuples and 73 capture tuples; this is not a long-lived bloat study.

After stopping the worker and running ANALYZE on the selected tables, three
warm read-only observations per shape produced:

| Query shape | Plan | Actual result rows | Execution range, ms |
|---|---|---:|---:|
| Due delivery | `actions_due` index | 0 | 0.005–0.016 |
| Due projection | `actions_projection_due` index-only | 0 | 0.003–0.016 |
| Exact source history | `actions_source` index | 1 | 0.004–0.007 |
| Most recent 50 | scan 500 + top-N heapsort | 50 | 0.099–0.110 |
| State counts | scan 500 + aggregate | 1 | 0.086–0.107 |
| Newest generation | `alert_generations_alert_seq` + one-row sort | 1 | 0.005–0.008 |
| Retirable staging candidates | alerts scan; 500 removed by filter | 0 | 0.100–0.109 |

Plans reported zero shared reads and zero temporary read/written blocks; these
were warm-cache observations. Planning time ranged 0.010–0.173 ms. Retirement
scanned 500 alerts despite returning zero candidates, using 364 shared buffer
hits; the row limit is not a bound on rows scanned. This is a scaling dimension
to measure at the owner-defined retention size, not proof of a current defect
or justification for an unsolicited index. The 500-row sequential scans and
empty due queues cannot establish loaded-worker performance or production
capacity. Raw exact SQL/parameters and plans remain in the verified private
successful archive; no plan or fixture was substituted after execution.

## Measurement method and limits

Retain all rows generated by the native 50/200-alert batches, including the
already-acknowledged populations. Record exact table counts, capture age range,
table/index size, live/dead tuple estimates, database/service versions, host
resources and worker state. Preserve raw plans in the private evidence stores.

After the batch, stop its worker and collect three warm-cache
`EXPLAIN (ANALYZE, BUFFERS, SETTINGS, FORMAT JSON)` observations per bounded
read-only query shape: due delivery, due projection, source-event history,
recent operator view, state counts, newest alert generation and staging-intent
retirement candidates. Use the candidate's actual columns, indexes and function
signatures. Record query parameters and ANALYZE timing; do not present these
selects as execution of the full locking/update worker or retirement function.

Report chosen plan, planning/execution duration and range, actual/estimated rows,
buffer hits/reads, scan/filter counts, sorting and spill. No aged rows are invented
and no rows are expired/deleted for this first assessment. An empty terminal-work
queue is useful only as an empty-queue baseline, not a loaded-worker benchmark.
Small-table sequential scans alone are not an index defect.

## Inputs required for representative retained-ledger qualification

The workload and records owners must supply:

- Intended retained days, capture/action volume per day, legal holds and deletion
  policy; distribution of young/old, settled/unknown/held/expired records and
  intents. G8 governs policy; arbitrary synthetic ages cannot authorize retention.
- Customer/instance/cohort counts, skew, hot-key/event reuse, active backlog,
  arrival and peak burst rates, read/write concurrency and realistic payload size.
- Approved hardware/storage, PostgreSQL/PgBouncer versions and settings, pool and
  per-instance budgets, maintenance/VACUUM/ANALYZE behavior and competing load.
- Reviewed latency, timeout/error, throughput and fairness targets, allowed
  resource headroom, maximum database size and qualification duration.
- Approved contained environment, bounded resource budget, private evidence
  destination/retention and an executor/reviewer for results.

## Concrete next measurement

Once those inputs exist, freeze the candidate and one dataset specification with
seed, scale, row ages/state mix and expected cardinalities. Use an approved
synthetic generator through valid schema constraints; isolate and label any
artificial aging. Never rewrite retained successful evidence or reuse source
events to manufacture new acknowledgement results.

1. Build at least the owner-defined expected retained volume and bounded peak
   scenario in the authorized lab. Record generation time, complete counts,
   relation/index sizes, distribution checks and fixture digest.
2. Measure the same plans before/after explicitly recorded statistics maintenance.
   Cover cold and warm observations only where cache control is valid; otherwise
   state that cold-cache behavior is unavailable. Use statement timeouts and
   capture every failure, cancellation and spill.
3. Exercise the actual candidate worker/retirement paths with the specified live
   backlog, arrival rate and concurrent operator reads. Measure queue age,
   progress/fairness, leases, waits/locks, DB/host resources and retained growth.
   Bound duration and stop on the approved resource/error limits.
4. Compare to the owner's targets, report p50/p95/max and uncertainty, and explain
   differences from the idle read-only baseline. Diagnose a demonstrated defect
   before proposing SQL, index, retention or concurrency changes.
5. Retain original attempts, dataset/command/plan records and private backup
   verification. Any necessary code change gets a separate claim and explicit
   affected-evidence revalidation decision; preserve the qualified old artifact.

Until representative inputs are supplied, this plan is prepared and the
production-like retained-ledger requirement remains pending. It does not block
other authorized ARM64 work or waive full T30/G6, G8 or deployment acceptance.
