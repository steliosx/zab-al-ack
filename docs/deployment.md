# Reviewed deployment procedure

**a9 namespace change:** read [RENAME.md](RENAME.md) before installation or rollback. This release uses a fresh `zabalack` database namespace and refuses an existing Ackline schema.

The supplied request authorised development and isolated lab work only. None of these procedures has been applied to production. The reference package has external writes disabled and no production cohort/endpoints. Gate evidence and commands run are recorded separately; inspect `acceptance_matrix.csv`, `deployment_gates.csv`, `compatibility_manifest.json`, `reference_manifest.json` and `SPEC_AMENDMENTS.md` before selecting targets.

## 1. Package and inventory

Verify `dist/SHA256SUMS` against the exact wheel/archive delivered. Use the repository Python/dependency pins, build command and test runner in README/AGENTS. Supply the consolidated inputs in `INPUTS_REQUIRED.md`. Run only the explicitly selected, authorised read-only collectors. A static configuration parser cannot establish effective runtime values or application/probe routing; capture runtime evidence separately. Do not install an unrecognised Alerta/Zabbix version or broaden grants automatically.

Stage a reviewed private Ansible inventory, an offline wheelhouse and the actual config/secret references. Keep all production URLs and cohorts out of distributed samples. The installed `zabalack --config PATH config-check` command parses configuration without resolving endpoint secrets or contacting targets. Secret files must be regular owner-controlled files with mode 0600 or stricter; the worker/service user must be their owner or able to read a root-owned protected file through an explicitly reviewed delivery mechanism. Do not use world/group-readable copies to work around this check.

`deploy/ansible/01_install_shadow.yml` selects no hosts by default, requires `zabalack_install_opt_in=true` and a change reference, stages the supplied wheel and config, and copies an inactive unit. It creates a dedicated worker virtual environment and never installs or upgrades Alerta. Dependencies must match the reviewed lock/wheelhouse. Alerta plugin installation goes into each existing Alerta runtime environment using the same wheel with `--no-deps`; first verify that its compatible pinned runtime dependencies are already present. No active service is restarted by the install playbook.

## 2. Database preparation and separate trigger authority

Choose the actual `alerts` owner and the authorised role-provisioning identity from G1. `sql/install/00_roles.sql` is reviewed one-time role/schema provisioning, not a runtime command; it contains no passwords. Existing roles require explicit comparison instead of rerunning or auto-broadening them. Confirm `zabalack_owner` neither owns `alerts` nor inherits its owner role, and has only the documented underlying projection-column grants. Record under G1 which role owns `alerts` and whether the Alerta application connects as that owner: `sql/migrations/005_readiness.sql` grants `EXECUTE` on `zabalack.capture_ack()` and `zabalack.seal_installation()` to the observed `alerts` owner, so where the application runs as the owner (the upstream default) the runtime role can also re-seal the readiness manifest. Prefer a dedicated installation principal that owns `alerts` and a separate login role for the application; if that split is not possible, treat the application role as inside the trusted administrative boundary and audit `seal_installation` calls.

Drain or fence all eligible acknowledgement paths during readiness changes; invalidate every probe cache and keep delivery disabled. Zab-al-ack migrations run as `zabalack_owner`, separately from trigger administration:

```sh
# ZABALACK_MIGRATION_DSN contains a reviewed libpq service reference, not a literal password.
ZABALACK_MIGRATION_DSN='service=reviewed_zabalack_migration' python sql/migrate.py --set-role zabalack_owner
# A5 stage two: the principals that may hold zabalack_owner. installer_roles is a comma-separated list of the
# installation logins that are members of it — empty where the migrations run as a superuser and none is.
psql -X --no-password --set ON_ERROR_STOP=1 --dbname 'service=reviewed_zabalack_migration' \
  --set installer_roles=zabalack_installer --command 'SET ROLE zabalack_owner' --file sql/install/09_installer_roles.sql
# A5 stage two: the Alerta application role's single entry point into zabalack, granted by the schema owner.
# alert_app_role is the role the application connects as (the alerts owner under the upstream default).
psql -X --no-password --set ON_ERROR_STOP=1 --dbname 'service=reviewed_zabalack_migration' \
  --set alert_app_role=alerta_app --command 'SET ROLE zabalack_owner' --file sql/install/12_application_grant.sql
# Run with the separately authorised alerts-owner/installer service. On a fresh install this seals the manifest;
# on an upgrade of an already-sealed installation run sql/install/13_reseal.sql as zabalack_owner instead.
psql -X --no-password --set ON_ERROR_STOP=1 --dbname 'service=reviewed_trigger_installer' --file sql/install/10_trigger.sql
```

`12_application_grant.sql` grants `USAGE` on `zabalack` and `EXECUTE` on `zabalack.stage_generation(text,uuid,jsonb)` to the application role and nothing else; the role gains no table privilege there and no other function from it (where the application connects as the alerts owner, that role already holds 005's `capture_ack()` and `seal_installation()` grants, one more reason to prefer a separate login role). The function admits one non-owner grantee: the script first revokes the entry point from every other, so changing the application role never leaves the former role's credentials able to stage, and records the grantee in `zabalack.installation.application_role`. That is safe only while no function in the schema is executable by `PUBLIC`, the generation fence admits no grantee but its owner, and the entry point's only non-owner grantee is the recorded role, holding `USAGE` on the schema, having no member of its own, and being — and able to assume — none of the `zabalack_*` roles, and executing nothing else in the schema and reading no table there, as itself or as any role it can assume. A member of the application role inherits its privileges or reaches them with `SET ROLE`, and stages through the entry point while the ACL still names one grantee (superusers excepted; they execute it regardless); an application role that can assume `zabalack_worker`, or that simply holds `EXECUTE` on `worker_call()`, verifies, holds and rejects captures without the verifier's signature check. A membership moves no ACL, so it moves no sealed digest either; a stray grant does move one, and reads unhealthy through the digests until someone re-seals — which every upgrade does — so the effective-rights assertion is what still holds afterwards. Where the application connects as the alerts owner, that role keeps 005's `capture_ack()` and `seal_installation()` grants, which the trigger and the installer need. The grant script refuses a role that cannot open a session before it records one, and since it is a single transaction that refusal rolls back the revoke above it, leaving the former grantee's credentials intact rather than taking the working one away and putting nothing in its place. It refuses a role in any of these positions, and `zabalack_owner` holds no `ADMIN OPTION` to revoke a membership with: have the role's administrator revoke it, or name a separate application role. All of it `capture_health()` asserts under `functions_ok`, and `13_reseal.sql` refuses to seal over any of it. The same assertions cover the schema's whole grant map, not only the application's corner of it: the grantees of every routine in `zabalack` — procedures as well as functions, since a `SECURITY DEFINER` procedure runs as its owner exactly as a function does — are exactly the ones the installation makes, read both ways — `worker_call(text,jsonb)` and `project(uuid)` to `zabalack_worker`, `operator_call(text,jsonb)` to `zabalack_operator`, `capture_health()` to `zabalack_probe` and `zabalack_operator`, `capture_ack()` and `seal_installation()` to the alerts owner, `stage_generation()` to the recorded application role, every other function to no one, and none of those grants *missing* either: a revoked `EXECUTE` leaves no unexpected entry for a negative rule to find while the role it answers to gets `permission denied`, and the migrations do not re-make a grant they already made — no relation in the schema admits a grantee at all — the fence's identity sequence included, where `UPDATE` is `setval()` and a sequence moved backwards gives a later staging a lower `seq` than an earlier one — every routine body is the one migration 008 shipped — the one property a seal cannot answer, since a re-seal records whatever it finds, so the expected digest is kept in `zabalack.installation.routine_bodies_md5`, which 008 sets at the end of itself and no seal writes (definitions alone, so the grant that follows does not disturb it; and 008 refuses to run at all on a sealed tree whose fingerprint has already drifted, so drift cannot be carried across the upgrade either); every routine here keeps its `search_path` pinned to `pg_catalog, zabalack`, which `ALTER FUNCTION … SET search_path` can move afterwards and through which a `SECURITY DEFINER` body would resolve an unqualified name; every routine anyone but its owner can execute is `SECURITY DEFINER`, since `SECURITY INVOKER` there does not weaken the boundary but removes the path, the operator's controls failing under the unprivileged caller while every ACL still reads right; no grant here carries `GRANT OPTION`, whose holder can make grantees of its own that the map — reading the grantee alone — would then accept (the function ACLs, the schema's own, and the owner's columns on `public.alerts`); the schema and every function and relation in it are owned by `zabalack_owner` (a `SECURITY DEFINER` function runs as its owner, so a reassignment hands it that role's rights); schema `zabalack` itself admits only the grants the installation makes — `USAGE` and no other privilege, to the three runtime roles, the alerts owner and the recorded application role, and to nobody else, so `CREATE` goes to the owner alone and `PUBLIC` gets nothing; and each of the three runtime roles still holds that `USAGE`, as does the alerts owner — a separate role wherever the deployment splits the application from it, without which 005's `capture_ack()` and `seal_installation()` grants and `10_trigger.sql` itself fail at schema access — without which its fully qualified call fails at schema access while every function grant below still reads exactly right (`12_application_grant.sql` revokes a former application role's `USAGE` with its `EXECUTE`, keeping the map equal to the record); the recorded application role can still open a session as itself — `rolcanlogin`, no connection limit of zero, and `CONNECT` on the database — since Alerta connects *as* that role and no member of it is permitted, so one that cannot connect leaves nothing able to stage at all behind grants that read exactly right (`rolvaliduntil` is deliberately not asserted: it binds password authentication only, and a certificate-authenticated role outlives it, as `pg_hba` is outside what any of this can read); the three runtime roles can still open a session — `CONNECT` on the database and no connection limit of zero, the same two things asked of the application role, since a limit of zero refuses every new session as flatly as a revoked grant — the last grant `00_roles.sql` makes that nothing asserted, and a silent one: revoke it and `capture_health()` answers normally through the probe's existing session while the worker never connects again (`zabalack_owner` is `NOLOGIN` and connects as nobody; the migration principal assumes it after connecting as itself); `zabalack_owner` still holds exactly the `public.alerts` grants `00_roles.sql` makes it — `SELECT` on `id`, `customer`, `status`, `attributes` and `update_time`, `UPDATE` on `attributes`, and nothing else: every other rule about that table is a prohibition, and a prohibition cannot see a grant that is *missing*, while `stage_generation()` is `SECURITY DEFINER` and runs as this owner, so without `UPDATE(attributes)` every acknowledgement is refused `zabalack_generation_unavailable`, and `public.alerts` is outside the schema `catalog_fingerprints()` hashes so no digest moves either — its `USAGE` on schema `public`, by contrast, fails *loudly*: `capture_health()` and `13_reseal.sql` reach `public.alerts` through that grant too, so both raise `permission denied for schema public` and the probe's caller treats the exception as a failure, and the re-seal now names the missing grant rather than leaving a bare permission error; none of the four `zabalack_*` roles is a member of any role at all — every other membership rule here reads inward, and this one reads outward: `GRANT <the alerts owner> TO zabalack_worker` lets the worker `SET ROLE` to it and write `public.alerts` directly, past the projection boundary, while `has_table_privilege()` stays false because it resolves *inherited* privilege and a `NOINHERIT` role inherits none of what `SET ROLE` still hands it; no role outside the recorded installer topology can act as any of the four, whichever it is and whoever the role — reach rather than the direct edge, since `SET ROLE` follows a chain and so does `pg_has_role(..., 'MEMBER')`, which is what refuses a member of a recorded installer rather than exempting it along with the installer — since a `NOINHERIT` member resolves no privilege through any ACL while `SET ROLE` hands it the role whole — an arbitrary login granted `zabalack_owner` reaches `worker_call()` and records a capture as verified with no signature check, and `catalog_fingerprints()` hashes a membership only where the *member* is itself one of the four, so an outside one moves no digest at all; each of the four keeps the attributes `00_roles.sql` declares — no `SUPERUSER`, `CREATEDB`, `CREATEROLE`, `BYPASSRLS`, `REPLICATION` or `INHERIT`, and `LOGIN` only for the three runtime roles, since an attribute is neither an ACL nor an ownership and walks past every rule above; and the installer topology is named rather than assumed: `09_installer_roles.sql` records in `zabalack.installation.installer_roles` the principals that may hold `zabalack_owner` — and only `zabalack_owner`; a recorded installer granted `zabalack_worker` is refused like any other role. Recording does not make an installer less powerful, since one that can act as the owner can rewrite the list; it makes the set of principals that can an explicit, reviewable part of the installation instead of an exemption for every role outside those four. The column starts `NULL` and the script is the act that sets it, empty where the migrations run as a superuser and no role holds `zabalack_owner` at all; an installation that never recorded its installers is not healthy and is not sealed. The script refuses a name that is not a role, a name that is one of the four, a name that does not actually hold `zabalack_owner`, and a role that does hold one of the four and was left out — naming them, and changing nothing, since `zabalack_owner` holds no `ADMIN OPTION` to revoke a membership with. Whoever reaches `worker_call()` claims verification leases and calls `verify_complete`, so a capture is recorded as verified with no signature check; whoever reaches `operator_call()` enables external writes, resumes instances, edits cohorts or activates capture bypass. Every one of those ACLs is hashed, so a stray grant reads unhealthy through the digests — the map is what still refuses it after the re-seal an upgrade performs. The grant changes ACLs the readiness manifest hashes, so it precedes sealing. The application refuses an acknowledgement with `zabalack_generation_unavailable` (503) while the grant is absent, so a plugin deployed ahead of it fails closed rather than staging without generation protection.

The migration runner checks migration SHA-256 records; an applied checksum mismatch aborts instead of replacing definitions. `02_zabalack_migrations.yml` (which also runs the application grant, as the schema owner), `03_trigger_install.yml` and `04_reseal.yml` are independently opt-in, select no hosts by default and do not start workers. Use role-specific test assertions after installation. A DBA/superuser provisioning success is not evidence for T35/T38/T39. A principal with only a TRIGGER grant is insufficient for physical disable/enable; use the actual table-owner authority for that separately controlled step.

Before unfencing, verify catalog attachment/mode, function identity/signatures, ownership/grants, metadata deployment identity, schema version and behavior under exact caller roles. Execute rollback/capture-failure branches in staging: PL/pgSQL branch validation cannot be proved by function creation alone. The health probe checks its own connection route; the application's committed canary capture establishes alignment with the separately pooled Alerta connection.

## 3. Shadow plugin rollout

The baseline installs all eight migrations into the fresh `zabalack` schema.
It includes the late-response fencing (006), settled-expiry (007) and generation-fence (008, A5 stage two) corrections.
Do not apply these files to an Ackline database. Historical Ackline a3→a4/a5
and a4/a5→a6 upgrade instructions are retained in the original a8 handoff;
they are not a9 transition instructions. See [RENAME.md](RENAME.md).

### Rolling installation

Keep `external_writes_enabled=false` in package config and the database write-disable policy. Load only reviewed pilot cohorts; never auto-populate them from incoming alert IDs/hosts. Enable capture only after its DB readiness checks pass. Configure the Alerta plugin via `ZABALACK_CONFIG_FILE` (JSON config path) in the existing application configuration. Entry points are `zabalack_zabbix_normalise` and `zabalack_zabbix_ack`.

Preserve existing plugins, authentication and routing. Add the normalizer at the reviewed inbound position, and ensure the signer is **last in every effective routed status chain**. Do not replace the entire `PLUGINS` list with an example. Audit notifications, observers, tracing and error handlers for precommit text/proof exposure. Unsupported paths remain local-only; do not patch repeat-Ack 409 into success.

Install the required application adapter after the application's logging setup and before serving requests. For an ordinary Gunicorn factory deployment, use the target `zabalack.plugins:create_app()` in the reviewed service command; it invokes Alerta's actual factory and then `configure_app(app)`. If a custom factory already exists, preserve it and wrap its completed application with `zabalack.plugins.configure_app(existing_app)`. Do not bypass existing config/auth initialization. Without this adapter an eligible acknowledgement fails closed with propagated 503. Source-backed amendment A1 in `SPEC_AMENDMENTS.md` documents the reference logging/signal exposure being closed. Review any logging handlers or instrumentation added after the adapter; unreviewed status signal receivers cause routing exclusion. The rollout must include real failed-save and precommit observer tests on every serving path.

Drain one API node at a time, install the reviewed package/config with a separate restart approval, verify hook routing and probe health, run synthetic capture/409/customer/unsupported-route checks, then return the node to service. Repeat for every serving node/site before permitting any source write. Validate identical configuration revision, key IDs, bypass state and writer routing across the fleet. Mixed bypass nodes remain drained.

Review `zabbix/v1/media_type.reference.json` against the real export in isolated Zabbix. Import the reviewed a9 artifact to obtain the new name and neutral-comment format. Ackline artifacts before 0.1.0a8 also require the absent-cause macro correction (`SPEC_AMENDMENTS.md` A3). It is disabled and is not a drop-in replacement. Preserve existing event/resource/correlation identity and matching actions. Gate G3 covers **all** update operations and all senders, including native email/command exclusions and action=2's no-comment case. Do not send canaries to real customer destinations.

Start the worker in shadow only after the reviewed systemd unit, credential references and schema checks are in place. `systemctl daemon-reload`, service start/enable and Alerta restarts are explicit separate operator actions; no install hook runs them. Synthetic cohorts/credentials remain lab-only. Review held work and projections; shadow operation can capture/verify evidence but never claim an API write succeeded.

## 4. Controlled enablement

Resolve source-backed amendments affecting external writes; complete and sign G1–G8 for the approved cohort. Run staging `deployment_acceptance.md`, including measured 50/200 per-alert batches, every API node, tenant negatives, update-operation effects, failover and PgBouncer. Validate the dedicated Zabbix token with authenticated exact-event reads and an explicitly authorised synthetic acknowledgement. `apiinfo.version` alone proves neither authentication nor tenant permissions.

Pause every configured instance, account for in-flight attempts, and verify both config and DB switches remain disabled until the change window. Provide a reviewed config with `external_writes_enabled=true`; this does not itself resume an instance. Use the operator CLI's explicit `enable-delivery` guard after reading its versioned `--help`, specifying instance, accountable owner and change reference. Enable one approved pilot instance; keep others paused. Record the exact reviewed config/cohort/policy hashes. No example or service restart invokes enable-delivery.

Run a synthetic end-to-end capture/delivery/projection canary within approved destinations; inspect write response evidence and neutral reference. Observe queue age, validation/write latency, API/DB/PHP load and one-incident-per-instance failure routing. Expand only by a new approved cohort revision and its tests. Concurrency defaults of two per logical instance are unmeasured starting values; no claim of production p95 follows from lab results.
