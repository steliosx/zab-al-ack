# Implementation decisions (baseline is unchanged)

1. The installable package is zabalack 0.1.0a13, using Python 3.12 in this build. Plugins use the inspected Alerta 9.1.0 interfaces; the worker and probe use Psycopg 3.2.10, while Alerta's own reference backend uses Psycopg2 2.9.10. Pins are in requirements.lock and requirements-runtime.lock. No dependency upgrade occurs on import/startup.
2. Wire encoding and bounds are documented in PYTHON_API.md and enforced in crypto.py. HMAC-SHA256 is the sole signature scheme. Signing keys are raw 32–128-byte protected files; generated production configuration contains only references and empty maps. A missing verification rotation key holds only affected captures. No key enters PostgreSQL.
3. Full canonical alert UUIDs qualify the supported single-alert route. Short-ID URL requests remain local-only even if Alerta resolves them to a full alert. No source lookup occurs on ingestion. Cohort policies are controlled snapshots; actor scope is authenticated Alerta context with an explicit configured administrative exception. Within-scope historical ingestion provenance is deliberately not claimed (T11b).
4. SQL uses restricted captures/outbox and separate verified actions/effects. A replay of an existing verified action keeps its identity. Distinct explicit human actions coalesce while the previous effect is unresolved. A later explicit action issued after completion creates a later effect generation. Retries never create identities, extend lifetime, or automatically re-ack a terminal effect after source unacknowledgement. A database identity sequence on capture establishes projection order even when action issuance times tie or verification is reordered; newer local-only skip projections have a separate local timestamp guard.
5. SQL function owners cannot attach or disable the Alerta trigger. The separate installer runs with the actual alerts owner authority. SECURITY DEFINER uses controlled search_path and same-transaction PUBLIC revocation. The worker accesses only function interfaces. Projection accepts an action ID, derives approved attributes from the authoritative ledger, and preserves all source keys; the trusted owner still has full JSON access inside its granted attributes column.
6. Async HTTPX performs one explicitly scoped JSON-RPC request with asyncio overall deadlines, exact response binding and bounded streaming. No retries or redirects are delegated to HTTP middleware. Durable attempt evidence precedes a source send. Unconfirmed ambiguous sends stay on read-only reconciliation; absence of a public reference does not prove a send did not commit. An operator cannot erase uncertainty by retrying. This conservative hold can require investigation but avoids blind duplicate comments. The operator-only settle-unknown control requires an explicit remote-fencing/settlement confirmation and evidence reference. It leaves unexpired work failed for a separately selected retry, expires stale work, and never sends automatically. The database does not claim to prove remote cessation from that attestation.
7. One instance-wide SQL background lease and one-second start interval cover reconciliation/host checks. Two delivery slots are the initial bound shared across sites; local worker tasks do not override it. The tested SQL coordination profile uses a 10-second verification lease, 30-second delivery lease and verifier bounds of four per worker/32 globally; differing Python coordination values are rejected instead of silently ignored. Tuning that profile requires a reviewed SQL migration and native batch acceptance. Fast queries and projection batches are capped at 200, host reads at 50 IDs. Native performance acceptance and tuning remain G6. Terminal source-effect state is retained on read failures; check errors cannot reopen it for delivery.
8. The versioned Zabbix media artifact is a reference implementation, not a validated replacement for the unsupplied live export. Zabbix 7.0 get_event_cause_value can leave the optional no-cause macro literal unresolved. The sender maps exactly that documented optional sentinel to null; unresolved required problem/trigger/recovery IDs are rejected. Notification update-operation inventories remain G3.
9. Fleet bypass readiness requires operational drain/fencing and verified configuration on every serving process. A probe checks its own database connection only. The local flag-based and separately privileged physical-trigger-disable procedures remain distinct, as described in final_review_notes.md. No fleet quorum or production gate evidence is invented.
10. No retention cleanup or destructive migration/rollback is supplied as a default action. Evidence is retained until G8 supplies an approved records policy. UI examples use existing attribute columns and filters; there is no new frontend or dashboard service.
11. This workspace cannot map a non-root native PostgreSQL process and provides no Docker/Podman. The provided native lab remains runnable elsewhere. Supplemental PGlite 0.5.8 executes PostgreSQL 18.3 compiled to WASM with the real upstream composite schema and SQL roles. Its single-session and wire limitations exclude native multi-session concurrency, cancellation, PgBouncer, failover and production permission claims. Every report identifies its actual evidence layer.

12. Capture order is a database-generated monotonic identity assigned in the acknowledgement update. Projection compares this order rather than relying on potentially equal/skewed API-process timestamps; it also preserves a newer local-only skip. Explicit audited `settle-unknown` requires an engineer’s remote fencing/settlement evidence, never infers non-execution from a timeout, and never sends a source request. A separate retry is required for eligible unexpired no-effect work; expired work still requires a later explicit human action. Source deletion must be independently confirmed. Non-uncertain expiry closes the old effect at its original deadline, preserving the ability to create a later explicit action without reviving the expired one.
